# ScoutCapture refactor plan

## Starting point

- Branch: `codex/refactor-test`, based on source commit `4e04061` (app version 1.2, build 19).
- The original `main` working tree has separate local edits and is not used for these changes.
- Primary cleanup goal: remove repeated production code and achieve a substantial net reduction in source lines while preserving Build 19 behavior. Moving lines into smaller files improves navigation but does not count as line reduction. Build 19 has **129,011 production Swift lines across 17 files**; this branch currently has **120,966 across 24 files**, a net reduction of **8,045 lines (6.2%)**. `AppState.swift` changed from 63,118 to 60,897 lines, `ScoutCaptureApp.swift` from 25,071 to 20,702, `ContentView.swift` from 19,800 to 16,210, and `LocalStore.swift` from 7,718 to 7,625. Track these totals after each cleanup and identify the duplicate logic removed.
- The prechange simulator test run produced 1,108 passes and 105 failures before one test stalled and the run was stopped. A later full run on the refactor branch reached 238 completed tests (208 passes, 30 failures across five classes) before it was stopped because offline-replay fixtures repeatedly contacted `example.supabase.co` and made the broad gate too slow and unreliable. Those failures are not yet attributed to refactor changes. One property-status failure reproduced in isolation (`testCachedExportedFreshRemoteOccupiedByOtherBlocksEntry`, cache status was `nil` instead of `occupied`). Tracing showed a startup authentication callback arriving after its fixture installed a fake user; that callback cleared the organization scope and status cache. Cancelling the startup callback when observation stops and stopping the unused observer in this fixture made the isolated test pass. The other prechange failures remain unclassified, so the full suite is not yet a reliable pass/fail gate.

## Test baseline investigation

After cancelling the stale authentication startup callback in the property-status test fixture, the full `Phase2C27FZ4PropertyStatusDiagnosticsTests` class ran to completion: **75 tests, 58 passing cases, 17 failing cases (35 failed assertions)**. The isolated case that first exposed the callback race passes, along with two neighboring entry tests. The initial failing cases clustered as follows:

| --- | ---: | --- |

| No-ZIP release and local reconciliation | 3 | Stale draft or released status remains visible; one persistent-data reconciliation assertion checked before a scheduled refresh completed. |
| User-facing lock wording | 6 | Tests expect older phrases such as “on device”; the app now renders a short bullet-separated description. |

Source history confirmed that the six lock-message tests expected older copy. After updating only those assertions, the full class reran with **64 passing and 11 failing cases (27 failed assertions)**. The missing-row test expected an older diagnostic reason and now passes in isolation. Four pending-export tests expected both a Pending Export badge and a Lock badge; Build 19 intentionally shows the Pending Export badge while still blocking entry, and all four pass with that expectation. The persistent-data reconciliation test checked before the app's 180 ms debounce; after waiting for the actual refresh, it passes. For no-ZIP release, the app correctly hides the stale current-device badge while retaining the remote cache record, and it preserves a lock owned by another device. The tests now verify those visible outcomes. A known empty local draft incorrectly showed a Draft badge; the compare answer now treats that current-device draft as a no-op, and adjacent owner and non-owner badge tests pass. The two remaining tests expected a same-user, different-device draft to be treated as owned locally. The current Build 19 policy treats the recorded device as owner, and the tests now assert its existing lock and cache behavior without changing runtime policy. The full class now runs **75 tests with 0 failures**. This class is one slice of the earlier 105-failure Build 19 run; the other failures are still unclassified.

One coordination failure, `testUntouchedLocalSessionOccupancyClaimWritesRemoteMarker`, also reproduced alone. Its fixture faked the occupancy write but not the newer `claim_property_status` RPC, so the app tried `example.supabase.co`, failed the status claim, released the occupancy marker, and blocked entry. The same fail-closed branch exists in Build 19. A Debug-only RPC response override now lets the fixture provide a deterministic success response; production continues to block entry if the real status claim fails. Two other tests held stale expectations: one expected the remote-occupancy message when the current local session is active, and a hand-written legacy queue payload omitted the required `is_archived` property field. With those test-only corrections, all **23 coordination tests pass**. The class still logs unrelated profile lookup attempts to the placeholder host, so it is not fully network-independent.

The full `Phase2C07bMediaBackfillTests` class now passes **54 tests with 0 failures**. Its older fixture created organizations without selecting one, while current media recovery limits inspection and retry to an active, accessible organization. The fixture now sets that context and stops its startup auth observer. Tests that switch organizations use the matching Supabase context; two audit tests pass fixed records to the audit helper so local refreshes cannot change their input mid-assertion. Diagnostic checks now verify the current retry-cap and redaction rules, including the case where a background metadata update removes optional error details. These are test-only changes; media backfill and recovery code did not change. Other broad-suite failures remain unclassified.

The full `Phase2C10OfflineReplayTests` class now passes **33 tests with 0 failures**. Its session-queue fixture now provides an idle status row and explicitly saves the new session shell before expecting a queued write, matching Build 19. Date assertions use whole-second timestamps because queue storage rounds timestamps; a global last-error assertion was removed because unrelated background network requests can replace it. The class also exposed one runtime bug: a permissions failure naming the `sessions` table was being marked as permanent parent-`properties` debt, stopping retries. Auto-acknowledgement and stale-parent classification now require an error naming `properties`, leaving sessions-table failures queued for retry and manual review. The diagnostic classifier now recognizes the hyphenated `row-level security` phrase.

`ClientPortalPriorityTradeSyncTests` originally had **7 failing cases out of 53 tests (11 failed assertions)** on both untouched Build 19 and the refactor branch. They were baseline test mismatches, not refactor regressions. The user reported that reopen and rejection worked in their last Build 19 check. The test-only fixtures and assertions were aligned with Build 19 rules: a timestamp-only overlay counts as applied; pending-review lineage does not write `observation_updates`; resolved and pending-review shots retain the issue marker; a generic `status_changed` activity is distinct from an explicit reopen; rejection keeps photo evidence; and metadata called stale is now dated before the rejection. The explicit reopen and rejection tests still pass. No portal runtime code changed. The full portal class now passes **53 tests with 0 failures** and is included in the combined smoke gate.

The local shot and lifecycle classes now pass **77 tests with 0 failures** after correcting one older expectation that a resolved shot loses its flagged marker; the same Build 19 path keeps that marker while its issue status becomes resolved. The six-test guided durability class initially had one failing completion-preparation assertion. The Draft badge assertion immediately before it passes. Build 19 requires an authenticated owner to start the upload phase, while this test deliberately disables authentication; the same completion-preparation assertion fails before the session metadata recovery refactor. The test now expects preparation to decline and checks that the completion marker and draft hiding still work. All **6 guided durability tests pass** without changing runtime behavior.

## Completed on the refactor branch

1. **Preset ownership.** One shared `DetailTypesModel` now serves standard and fast capture. The second model and its duplicate persistence logic were removed. Focused tests cover cross-view edits, persistence, and fast capture's Overview selection.
2. **Credential exposure check.** A value-redacting scanner checks tracked files and optionally a built app for recognizable privileged keys. A pull request workflow runs the source scan. The current source and Build 19 / refactor Debug and Release app bundles contain no recognized privileged credentials. The Supabase publishable key remains in the app as a public client identifier.
3. **ZIP export code.** Three in-memory ZIP writers and duplicate entry readers were consolidated into `StoredZipArchive`. Focused tests and an independent ZIP reader verified archive paths, file contents, and checksums. ZIP32 bounds now fail explicitly.
4. **Export memory use and migration ZIP.** Export enumeration keeps file URLs rather than all photo bytes. The active export paths stream ZIP contents in 64 KiB chunks, copy staged photos at the file level, and read only the ZIP directory during validation. The temporary migration export now uses the same streaming ZIP writer while preserving its directory entries and per-entry progress updates. A standalone optimized writer check with 64 files totaling 128 MiB found temporary read buffers accumulating to about 278 MB peak memory; releasing them per chunk reduced measured peak memory to about 8 MB. An independent ZIP reader verified all 65 entries and checksums, and focused app ZIP tests pass. This measures the writer process, not the full app export flow.
5. **Migration import path safety.** The importer now validates every Application Support and Documents file path before replacing local data. Traversal, absolute-like, repeated-separator, backslash, and control-character paths fail import. Focused tests verify valid nested paths and that a malicious archive leaves existing preferences intact.
6. **Backend configuration extraction.** `SupabaseRuntimeConfiguration`, cutover phase and rollback descriptions, and `BackendFeatureFlags` moved unchanged from `AppState.swift` into `BackendConfiguration.swift` (561 lines). ## Next steps, in order

1. **Restore a trustworthy test baseline.** The expanded nine-class smoke gate passes **270 tests with 0 failures**, including all 53 portal cases and the six guided durability cases. Group and reproduce the remaining prechange failures outside this gate, identify shared simulator or test-data contamination, and establish a full-suite gate. Do not attribute existing failures to the refactor.
2. **Validate archive integration at realistic size.** The shared writer passed a 128 MiB standalone archive check, and the actual package path passed a 200 MiB synthetic photo check. Next exercise the full app export UI with a large real photo set and compare its layout with Build 19. Keep ZIP32 limits visible to users or add ZIP64 support if real sessions can exceed them. Migration restore now streams files and uses the shared ZIP directory reader. Path and payload integrity preflight run before local data is cleared; a fully atomic replacement still needs a separate design.
3. **Remove remaining duplication for net line reduction.** Prioritize repeated production paths in the three largest files: `AppState.swift`, `ScoutCaptureApp.swift`, and `ContentView.swift`. Standard and pending ZIP packaging already share a helper, and standard/fast ZIP naming is shared. Continue consolidating repeated report packaging, file naming, and state-transition logic in small steps. Record production Swift line counts before and after each step; a file split alone does not meet this goal.
4. **Split `AppState` where it enables shared logic.** Snapshot status and diagnostics models, offline retry rules, and the duplicated session finality and capture-count rules now have their own files. Extract state transitions and synchronization policies behind narrow interfaces when that lets repeated implementations be replaced with one, with characterization tests. Avoid a whole-file rewrite of the remaining large type.
5. **Consolidate configuration.** The typed backend settings now have their own file. Consolidate scattered environment overrides and diagnostic redaction into that layer where this removes duplicate rules, with characterization tests for precedence and production rollout gates.
6. **Protect security boundaries.** Review deployed Supabase RLS and storage policies against the checked-in migrations; verify service-role credentials remain only in server environments. The checked-in migration creates `scoutcapture-originals` as a private bucket, while app code uploads and downloads directly with the client. No `storage.objects` policy for that original-photo bucket appears in the checked-in migrations; the object policies present there target the separate `scoutcapture-session-snapshots` bucket. Inspect the live original-photo policy state before changing storage behavior. The repository and app bundle scan cannot prove the live database policies are deployed or correct.
7. **Add continuous verification.** Run the chosen smoke suite, archive tests, and credential scan on pull requests. Add a built-app credential scan in a build environment with enough storage.

Each extraction should be a separate commit with a build, focused behavior tests, and a review of user-visible export or capture behavior before merging to `main`.
