# ScoutCapture account deletion audit

Status, 2026-09-28: the five SQL migrations are live; the portal worker and single-account pilot are deployed; the disposable account deletion worker reported `completed` and an ensuing run was idle; user-visible sign-in and retained-data checks are pending. General deletion remains disabled pending completion checks. The current iPhone development build is installed. The iOS app and portal use the same Supabase Auth project and user ID. The sections below preserve earlier audit findings and inventory; for current launch gates see the portal repository’s `docs/account-deletion-launch-checklist.md`.

## Baseline findings before implementation

1. **There was no deletion flow at audit start.** The portal has no Manage Account route or authenticated deletion API, and the iOS app has no deletion entry point. Removing a membership only revokes organization access; it leaves the Supabase Auth account and its other organization memberships intact. The portal invite acceptance creates or updates the Auth user, ensures `users_profile`, and grants a membership (`Scout Website/api/_portalInviteShared.js`).

2. **Calling `auth.admin.deleteUser()` directly is unsafe and likely to fail.** `users_profile.id` cascades from `auth.users`, but most references to `users_profile` have the default `NO ACTION` behavior. Blocking examples include `org_memberships.user_id`, `property_access_grants.user_id` and `granted_by`, `org_invitations.invited_by`, `punchlist_activity.created_by`, and `report_package_email_notifications.recipient_user_id`. Nullable attribution references such as `updated_by`, `session_events.actor_user_id`, `session_snapshots.created_by`, and `portal_invites.accepted_by` also block until handled. Only `report_email_user_preferences.user_id` explicitly cascades. Sources: `supabase/migrations/202604090001_phase_2c_02_canonical_schema_v1.sql`, later ScoutCapture migrations, and `Scout Website/supabase/migrations`.

3. **Personally identifying text exists beyond the profile.** `portal_invites.email`, `org_invitations.invitee_email`, `report_package_email_notifications.recipient_email` and `recipient_name`, and possibly free-form activity notes and `session_events.payload` need a retention/redaction rule. UUID nulling alone is insufficient. Report-ready email outbox rows must be canceled or suppressed before deletion so the user does not keep receiving messages. For the safer launch policy, remove former-user email/name from retained organization activity too, unless a specific retention obligation has been documented.

4. **Uploaded files need a separate inventory.** The app uses private Supabase Storage buckets for originals and session snapshots; the portal also uses deliverables and punch list attachments. Supabase states that Auth deletion fails while the user owns Storage objects. Some files are shared organization artifacts, so ownership and content policy must be decided before deleting or reassigning them.

5. **Sign-out does not clear device files.** `AppState.signOut()` signs out locally and clears access context/cursors, while `LocalStore.wipeAllLocalData()` is called by a separate local reset path. The active local store is under Application Support; optional/manual iCloud backup and legacy cloud paths also exist. A portal deletion cannot erase data already stored on other devices. The app needs a deliberate local cleanup flow and clear disclosure about other device copies/backups.

6. **Access can be cut off before final deletion.** The current organization RLS checks active `org_memberships`, so removing or marking all of a user's memberships deleted revokes organization data access even while a JWT remains valid. Supabase warns that deleting an Auth user does not invalidate already issued JWTs until expiry. A deletion process should revoke membership first, stop queued emails, then complete record/file cleanup. Server endpoints must reject deleted/pending users regardless of cached JWTs.

7. **The account page must work without report access.** Portal report routes depend on a Reports Portal role. A signed-in user with only Scout Capture access, or whose last organization membership was revoked, still needs to reach Manage Account and complete deletion. Use a standalone `/account` route authenticated by Supabase Auth, independent of report/admin permissions. Link directly to `/account` (or `/account/delete`) from iOS.

8. **Platform admin and organization owner are separate concepts.** The portal recognizes configured admin emails as platform admins and `ensureRequiredAdminOrgAccess()` adds/repairs owner memberships for those accounts when an admin loads the access page or creates an organization. The existing admin flow also guards against removing the last owner. The deletion service must check actual active owner memberships at request time; the email allowlist alone does not prove an owner row exists. Sources: `Scout Website/api-lib/portalAdminAccess.js` and `Scout Website/api/admin/portal-access.js`.

## Owner decisions recorded 2026-09-28

- Preserve shared captures, reports, punch list activity, and organization history while the organization has active customer users, with the business-record policy clearly disclosed. If the final customer user leaves, retain the organization temporarily under the 90-day proposal below, then purge its data. Do not treat ScoutClear platform-admin memberships as active customer accounts for that clock.
- For the safer App Review approach, remove the former contributor's email, name, Auth user ID, and other identifying attribution from retained activity and metadata. Show a neutral label such as “Deleted user.” Do not keep a lookup key that can silently restore the identity. The owner proposed this change after the initial request to keep email attribution.
- The owner currently has admin/owner access for every organization. No change to that operating model is requested. A deletion request can proceed without owner transfer **if a different active owner membership really exists** for each affected organization. If none exists, assign an owner or retain the organization under a clearly defined platform-admin custody workflow before deleting the account.
- **Review nuance:** Property photos and reports are scoped to the organization in the schema and intended as business records. That supports retaining them for remaining organization users after deleting the contributor's account and personal attribution. The schema does not establish legal ownership by itself; customer terms and deletion copy should say that the organization controls these records. Apple's FAQ broadly mentions shared user-generated photos, so a reviewer could still ask about the distinction. Photos or metadata that contain identifiable people need separate handling. Apple: https://developer.apple.com/support/offering-account-deletion-in-your-app

## Chosen launch policy for organization records

- An individual can initiate and complete deletion from the app/portal without emailing support. Delete the shared Auth identity and profile and remove email/name/user-ID attribution. Existing shared work in an active customer organization stays available to its remaining users, with a neutral former-contributor label.
- When an organization has **no active customer memberships**, start a 90-day organization-data retention clock from the last customer departure. ScoutClear's required admin/owner memberships do not keep that clock from starting. At the deadline, purge organization captures, reports, activities, and Storage objects automatically unless a documented retention obligation or active legal hold applies. Give the organization's verified contact a way to request earlier deletion by emailing the admin; verify authority before purging shared company data.
- Tell users the precise split and deadline in the deletion screen and privacy policy. An optional email for earlier organization-data cleanup cannot replace self-service account deletion. Apple permits manual processing with a stated timeframe but says ordinary apps should not require a support email or call to delete an account.
- **App Review uncertainty:** Apple's FAQ broadly includes shared photos and text in account deletion. ScoutCapture should explain that property captures/reports belong to the organization and remain available to its users after an individual deletes a login. Remove account-linked metadata and review any genuinely personal photo content. State the 90-day organization cleanup policy plainly. The owner elects to proceed without a lawyer review for now; App Review approval cannot be guaranteed.

## Recommended deletion contract

- "Delete account" means delete the shared Supabase Auth identity and personal profile, revoke access across **all** organizations and both products, and remove associated personal data unless a documented retention obligation applies. It is not the same as revoking one organization's access.
- Require a fresh authentication/confirmation step and show the cross-product effect. Check for another active owner in every affected organization. If absent, establish a replacement owner or custody path without leaving the user unable to initiate deletion indefinitely.
- Use an authenticated server endpoint keyed to the caller's Auth user ID. Never accept a target user ID or email from the browser. The service role key stays server-side. Make the workflow idempotent and resumable, with a durable status record and completion notice.
- Sequence: validate request and owner status; immediately revoke all active memberships and pending notifications; reconcile profile foreign keys and retained organization records; delete or reassign Storage objects according to policy; hard-delete Auth user; clear current browser/app session and local app data; confirm completion. Do not display "deleted" until the Auth deletion and cleanup have succeeded.
- Use schema migrations for explicit `ON DELETE` behavior or a controlled cleanup function. Preserve organization projects, reports, images, and activity under the recorded business requirement, under the chosen organization-record policy and its disclosures. Strip person-identifying attribution; avoid keeping `users_profile` or Auth rows as a stand-in for historical attribution.

## Decisions before enabling deletion

1. **Organization data terms:** Confirm that customer terms treat property captures, reports, and activity as organization records, identify any content containing personal details, and state what the deletion screen/privacy policy will say about active-organization retention and the 90-day inactive-organization cleanup.
2. **Ownership:** Confirm active admin owner membership exists in each live organization. Determine who receives ownership of retained Storage objects and how an unexpected sole-owner organization is handled.
3. **Backup scope:** Should deletion clear the current device's local files and app-created iCloud backup, and what guidance should be shown for other devices and platform backups?
4. **Processing window and notice:** What completion deadline and support contact should the UI state for account deletion cases needing manual review? What minimum deletion-request receipt may be retained, and for how long? Define the verified organization contact and legal-hold exceptions for early or scheduled organization purge.

## Verification plan

- In a disposable Supabase project seeded with both repo migrations, test a user with each FK role, owned Storage objects, pending emails, and multiple memberships. Assert the deletion job finishes without broken constraints or orphaned personal data while retained org records remain usable.
- Test ordinary member, no-membership user, sole owner, and multi-org user. Verify deletion from portal and initiation from app both work, that old passwords cannot authenticate, and that an old JWT cannot read org data after immediate membership revocation. Test the 90-day clock excluding ScoutClear admin memberships, earlier verified-contact purge, and cancellation/reinstatement if a customer organization becomes active again.
- Verify current-device data is cleared only after successful or explicitly pending deletion, and that the user sees accurate status/confirmation. Test retries after a failure between database cleanup, Storage cleanup, and Auth deletion.

The owner reports that the visible uploader email appears on the Reports tab rather than in the PDF. Code inspection supports that distinction: the checked-in property, flagged, and comparison PDF renderer plans do not consume actor email fields; the portal API computes `capturedByEmail` from snapshot/report metadata for the Reports tab. The local rewrite and readback process is implemented and unit tested; it still needs end-to-end Supabase and app restore validation before enabling deletion.

Automatic organization purge therefore needs an explicit, transactional child-first delete order plus Storage API cleanup. The summary does not include the remaining preflight result tables or Storage bucket counts; no purge has been enabled.

## Live Storage inventory, 2026-09-28

The owner supplied a read-only bucket summary: `scoutcapture-deliverables` has 815 objects and 0 owned objects; `scoutcapture-originals` has 656 objects and all 656 are owned; `scoutcapture-session-snapshots` has 326 objects and 156 owned objects. These are aggregate project counts, not counts for any particular user or organization. An individual deletion must transfer ownership of retained organization originals and owned snapshot objects through the Storage API before deleting Auth; deliverables do not need ownership transfer but still need inclusion in the 90-day organization purge. A purge must enumerate files using verified organization paths and database row references, never infer its target files from the aggregate counts. In particular, original photo paths are `sessions/<session-id>/shots/...` and contain no organization ID. The purge must join the session ID back to the target organization before deleting originals. Snapshot and PDF paths begin `orgs/<org-id>/...`; portal completion photos use `punchlist-completions/orgs/<org-id>/...`. No live Storage operation has been run.
